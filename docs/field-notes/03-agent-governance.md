# 03 · 管理與治理：把 agent 當成可管理的工作角色

「多 agent」不是替團隊多開幾個聊天網站，而是把不同工作責任拆成能被授權、觀察與收回的角色。對同事而言，所有請求與結果都留在 Lark；採購、客服、研究、開發與 IT 的資料來源、可用工具與可承受風險則在後端分開，避免混成一個全能 bot。

## 六個治理原則

| 原則 | 實際做法 |
| --- | --- |
| 一人一個專屬 agent | 每位同事都有獨立 agent；它可有單一專長或不同能力組合，而不是所有人共用同一個全能 bot。 |
| 權限要最小化 | Lark app scope、工具、資料來源與瀏覽器登入態依人／agent 切開；能讀資料不代表能寄信、建單或改權限。 |
| 瀏覽器操作對本人可見 | agent 操作真實網站時，使用對應同事可看見的[修改版 KasmVNC Chrome](../../docker/chrome/README.md)工作階段。使用者能看到正在做什麼，必要時可暫停或直接接手，而不是讓 agent 在看不見的黑箱裡操作。 |
| Vaultwarden 必須由本人解鎖 | 需要網站登入資料前，使用者先在自己的 KasmVNC Chrome 解鎖 Vaultwarden；agent 才能在同一個已解鎖的 session 使用被允許的登入資料。vault 重新鎖定後，agent 也不能再使用，且永遠拿不到主密碼。 |
| 高風險動作要可停 | 對外送出、付款、刪除、改權限、第一次登入與不確定的例外，都回到 Lark 請人確認，或由真人直接接手瀏覽器。 |
| 過程要能回看 | 任務、草稿、確認與結果留在 Lark 群組、文件或 Base；後端 project 記錄只保存必要的執行上下文。這不是為了監視，而是讓下一位處理的人能知道做過什麼、為什麼這樣做。 |

## KasmVNC 與 Vaultwarden：讓網站操作可見、可停、可收回

agent 不會在使用者看不到的瀏覽器裡保存登入狀態或自己找密碼。需要操作真實網站時，使用者先開啟自己的 [OSSLab-agent 修改版 KasmVNC Chrome](../../docker/chrome/README.md)，它和專屬 agent 共用同一個 browser session：使用者可以看到畫面、觀察操作進度，遇到 2FA、CAPTCHA、付款或不確定步驟時直接接手。

若網站需要帳密，**先由使用者在這個 KasmVNC Chrome 裡解鎖 Vaultwarden**。解鎖只是允許 extension 在目前 session 提供已授權的登入資料；agent 不會讀取、記錄或輸出 Vaultwarden 主密碼。使用者重新鎖定 vault 或結束 session 後，agent 的網站登入能力也隨之收回。

## 管理的單位是工作流，不是模型

模型可以換，工作流不能失控。OSSLab-agent 以 Codex、Grok 等**訂閱制** runtime 執行專屬 agent；真正需要長期管理的是：哪一個 Lark 使用者／群組可以叫到哪一個 agent、它有哪些特性與能力、能使用哪些工具、資料要留在哪裡、碰到什麼情況必須交回人。

這樣做還有一個很務實的好處：問題發生時不必先爭論模型「聰不聰明」。可以直接檢查任務路由、scope、輸入資料、審核點與瀏覽器 session；問題落在可修正的系統設計，而不是放大成對 AI 的不信任。

## 管理者以 Git 細緻管理 agent

每個專屬 agent 的特性、能力、工具 scope、資料邊界、runtime 與部署設定都以 Git 記錄在 Forgejo。**只有管理者**能修改這些設定；一般同事只在 Lark 使用自己的 agent，不會透過對話直接擴張能力或改寫權限。每次調整都留下 commit、diff 與必要的審閱紀錄，因此可以清楚知道某個 agent 何時被賦予什麼能力、為何變更、需要時如何回復。

這也是只採訂閱制 runtime 的理由之一：Codex、Grok 等訂閱制 agent 的成本能隨帳號與工作角色管理，不需要把每一個 agent 的使用量都變成難以預估的純 API 帳單；因此不採 OpenClaw 或 Hermes 這類架構。

## SSO 和 agent 權限是兩件事

Lark SSO 解決的是人員身分與登入生命週期；agent 權限處理的是系統可以代表誰做什麼。兩者不能互相取代。

例如，IT 同事能以自己的企業帳號登入 Termix，不代表任何 IT agent 都應取得同一把 SSH 金鑰；業務同事能在 Lark 群組要求產出報價草稿，也不代表 agent 應直接把信寄給客戶。登入、授權、執行與稽核四件事分開，才有辦法在擴大使用時維持秩序。
