# 03 · 管理與治理：把 agent 當成可管理的工作角色

「多 agent」不是多開幾個聊天視窗，而是把不同工作責任拆成能被授權、觀察與收回的角色。採購、客服、研究、開發與 IT 的資料來源、可用工具與可承受風險不同；混成一個全能 bot，短期省設定，長期一定難以追蹤。

## 四個治理原則

| 原則 | 實際做法 |
| --- | --- |
| 角色要清楚 | 以工作流或 project 配置 agent，而不是以「最強模型」作為唯一分工。每個角色知道自己該查什麼、不能碰什麼。 |
| 權限要最小化 | Lark app scope、工具、資料來源與瀏覽器登入態依角色切開；能讀資料不代表能寄信、建單或改權限。 |
| 高風險動作要可停 | 對外送出、付款、刪除、改權限、第一次登入與不確定的例外，都回到 Lark 請人確認，或由真人直接接手瀏覽器。 |
| 過程要能回看 | 任務、草稿、確認與結果留在群組或 project context；不是為了監視，而是讓下一位處理的人能知道做過什麼、為什麼這樣做。 |

## 管理的單位是工作流，不是模型

模型可以換，工作流不能失控。osslab-agent 把 Claude Code CLI、Codex CLI 等 runtime 視為可替換的執行者；真正需要長期管理的是：哪一個入口可以叫到哪一個 agent、它能使用哪些工具、資料要留在哪一個 project、碰到什麼情況必須交回人。

這樣做還有一個很務實的好處：問題發生時不必先爭論模型「聰不聰明」。可以直接檢查任務路由、scope、輸入資料、審核點與瀏覽器 session；問題落在可修正的系統設計，而不是放大成對 AI 的不信任。

## SSO 和 agent 權限是兩件事

Lark SSO 解決的是人員身分與登入生命週期；agent 權限處理的是系統可以代表誰做什麼。兩者不能互相取代。

例如，IT 同事能以自己的企業帳號登入 Termix，不代表任何 IT agent 都應取得同一把 SSH 金鑰；業務同事能在 Lark 群組要求產出報價草稿，也不代表 agent 應直接把信寄給客戶。登入、授權、執行與稽核四件事分開，才有辦法在擴大使用時維持秩序。
